# Findings

## REQUEST_CHANGES

1. `crates/dh-worker/src/service.rs:3099` accepts the request `MachineConfig`, `crates/dh-vmm/src/kvm.rs:333` installs a freshly computed KVM-masked CPUID table on the vCPU, and `crates/dh-worker/src/service.rs:3129` hashes the request config without checking that `config.cpuid_table` matches the table actually installed. `MachineConfig::new` still defaults `cpuid_table` to empty at `crates/dh-vmm/src/config.rs:244`, validation only checks size/sort order at `crates/dh-vmm/src/config.rs:283`, and proto mapping just copies whatever the caller supplied at `crates/dh-worker/src/proto_map.rs:191`. This leaves two deterministic-class failures: an empty table can pass and omit the live CPU surface from `machine_config_hash`, and a stale/non-masked table can be hashed while the guest runs different CPUID. Fix by deriving or validating the CPUID table at VM creation/restore against `cpuid::to_leaves(masked_cpuid(...))` before computing the config hash and state-hash chain.

2. The Linux trace acceptance does not fail on the new "unclassified" buckets. `tests/determinism/tests/linux_boot_trace.rs:156` records `unclassified_denied_msr_indices`, `unclassified_mmio_addresses`, and `unclassified_irq_timer_exit_counts`, and `tests/determinism/tests/linux_boot_trace.rs:631` serializes them, but `linux_entry_smoke` only asserts "not fatal before first serviceable exit" and file existence at `tests/determinism/tests/linux_boot_trace.rs:95`. A run with an unclassified denied MSR, MMIO address, or IRQ/timer exit would still pass. The checked-in/live artifact I found under `target/m9/linux_boot_trace.json` currently has those fields empty, but the test itself does not prove that. Add hard assertions for the unclassified sets/counts, and preferably for an expected terminal reason such as the icount limit, when `DH_M9_TRACE_BOOT=1`.

No additional behavioral regression found in the added denied-MSR action policy or the CPUID `ARCH_CAPABILITIES` bit mask itself.
