# 01-critical-and-important.md

Critical: `crates/dh-worker/tests/m5_frame_scheduling.rs:247` accepts `GuestHalted` or `HardCap` with `frames_elapsed == 0` as success. Risk: the current verified run passes with `reason=6` and `frames_elapsed=0`, so it never observes a Linux `FRAME_MARK`, never reaches the scheduled `at_frame`, and does not prove M5 frame scheduling across restore. Recommended fix: require `BudgetReached` and `frames_elapsed == 1`, then take/seal a post-run snapshot and assert the frame counter/log evidence advanced from `ready_frame_counter` to `ready_frame_counter + 1`; if the current Linux fixture cannot emit frames, this bead should be blocked or use a fixture that does.

Critical: `crates/dh-worker/tests/m5_net_loopback.rs:433` and `crates/dh-worker/tests/m5_net_loopback.rs:565` do not connect the pv-blk overlay operation to the replayed worker segment. Risk: `exercise_linux_pvblk_overlay()` writes/reads a standalone `PvBlk` with a discarded `LogWriter`, while `VerifyReplay` checks only the unrelated READY boot DHILOG and state hash; the test can pass even if worker-runtime pv-blk replay/BLKO restore is broken. Recommended fix: drive the pv-blk write/read through the worker/KVM path, seal that exact segment, run `VerifyReplay` on that log, assert `VerifyDone.end_state_hash` equals the post-IO snapshot hash, and compare BLKO before/after/replay evidence for the overlay state.

Important: `crates/dh-worker/tests/common/mod.rs:532` and `crates/dh-worker/tests/m5_net_loopback.rs:592` discard `VerifyReplay` `EpochOk` progress and only assert the stored DHILOG contains an `EPOCH_HASH`. Risk: this does not prove this gate actually observed epoch verification progress for the replay it just ran. Recommended fix: have `verify_replay_done()` return the `EpochOk` count and assert it is nonzero and matches the parsed `EpochHash` record count.
