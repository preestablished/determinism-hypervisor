Critical:
- `crates/dh-vmm/src/boot.rs:238`, `crates/dh-vmm/src/boot/linux_bzimage.rs:292`: The loader treats `payload_offset/payload_length` as the bytes to place at `LINUX_KERNEL_LOAD_GPA`, then enters at `LINUX_KERNEL_LOAD_GPA + 0x200`. In the Linux boot protocol, `payload_offset` is relative to the beginning of the protected-mode code and points to the possibly compressed payload; it is not the beginning of the protected-mode kernel image. This skips the decompressor/startup bytes before the payload and makes `RIP` land inside payload data for real bzImages. Suggested fix: copy the protected-mode portion from `setup_bytes..` to `0x100000`, reserve based on protected-mode length and `init_size`, and use `payload_offset/payload_length` only for validation/metadata. Add a fixture test that proves bytes before `payload_offset` are loaded and a live smoke that actually runs far enough to catch a bad entry.

Important:
- `crates/dh-vmm/src/boot/linux_bzimage.rs:624`: `build_boot_params` bulk-copies the source setup header and only overwrites selected fields, leaving unsupported write/special fields such as `setup_data`, `hardware_subarch`, and `hardware_subarch_data` to pass through if present in the image. This can make Linux follow a setup_data pointer or non-PC subarch path the deterministic subset did not construct or hash as a separate boot artifact. Suggested fix: explicitly reject nonzero unsupported fields during parsing, or zero all write-owned/special fields before setting the supported subset.
