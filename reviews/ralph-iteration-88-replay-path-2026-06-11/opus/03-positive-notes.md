# Positive Notes

### The reseal hammer is the right strength model

Layering granular per-record/per-epoch checks (for diagnostics) underneath a single
byte-identity assertion on the resealed log is exactly the correct design. The module doc states
it plainly: the per-record checks "exist for granular divergence reporting, not extra strength."
The byte-identity check subsumes everything — including AUX records the per-record path never
inspects (FRAME_MARK, NET_TX, ENTROPY), whose icounts and ordering are regenerated by the
replay's own rail at exits and must match iff execution matched. This is the strongest equality
the layer can state, and it states it.

### Restore INTO THE RAIL'S BUS — a real design catch, correctly resolved

`restore_snapshot(..., &mut rail.bus, ...)` (lines 289-300). The module comment captures why a
separate restore bus would be a silent bug: "a separate restore bus would leave the rail running
default devices." The rail dispatches every exit through `rail.bus`; the restored device state
must live there or the replayed machine runs fresh-booted devices against snapshot RAM. This is
the kind of subtle composition error that produces a divergence with no obvious cause, and it was
caught and documented.

### Entropy seeding faithfully implements §3.1

`rail.entropy = if header.entropy_seed == [0u8; 32] { restored.entropy } else {
DetEntropy::from_seed(header.entropy_seed) }` (lines 302-306). Zero seed continues the snapshot's
PRNG (the restored ENTR state); nonzero seed starts a fresh deterministic stream. This matches
the recording side and the §3.1 contract, and discharges the bead's "feed entropy from ENTR
state" requirement precisely.

### Quantization independence is genuinely exercised, not just claimed

Replay quantizes by record (`run_to` per canonical record + a tail to `end_icount`); the
recording quantized in fixed 100k budgets. The test asserts `records_applied == 2`,
`epoch_hashes_verified == 10`, AND `resealed == rec.log`. Because the epoch grid is absolute in
counter space and the chain folds register state at each grid point, the two differently-
quantized runs produce identical EPOCH_HASH sets and an identical sealed log. This is the
load-bearing property of the whole product, and the test proves it on real hardware rather than
asserting it in prose.

### The negative tests are honest, not tautological

The poisoned-RAM negative is the *correct* mismatch model, and the test comment shows real
understanding: a poisoned chain SEED would "travel through TIME and stay self-consistent" — it
would re-derive the same divergent-but-internally-consistent chain and NOT diverge, so it would
be a false negative. Poisoning guest RAM after the snapshot instead means the recording's hashes
describe a machine the restore cannot reproduce, so replay genuinely diverges at the first epoch.
Choosing the RAM poison over the seed poison is the difference between a test that proves
something and one that proves nothing. The foreign-config negative is refused at the header
*before any restore*, exercising the cheap-rejection path independently.

### EPOCH_HASH ordering and monotonicity are airtight

I verified the full chain: `aux()` preserves file order (= normative `(icount, seq)` order);
the sink fires in strictly increasing icount order within a quantum and quanta run sequentially,
so `verified` advances in exactly the recording's emission order; two PAD_SETs at one boundary
work because `run_to(target == start)` returns `Ok` and the reader's `IcountRegressed` only
trips on strict regression. No misordering window exists.

### The watermark/sink-conversion rationale is documented where it will be read

`runctl.rs` and `recording.rs` both now explain *why* the sink fires at the link point: the
DHILOG icount watermark is monotone, and post-quantum batch-landing "would interleave them BEHIND
later exit records and the writer rejects the regression (measured in iteration 88)." Tying the
API shape to the concrete `IcountRegressed` failure it prevents is exactly the kind of comment
that stops a future refactor from reintroducing the bug.

### END/header consistency is enforced upstream, so the engine can trust the header

The reader (`reader.rs:473-482`) cross-checks the END record body against the header
(`icount != header.end_icount`, `end_state_hash != header.end_state_hash` → `EndMismatch`). So
`replay_segment`'s reliance on `header.end_icount`/`header.end_state_hash` is sound: a header/END
mismatch cannot reach the engine, it is rejected at `parse`. The engine correctly does not
re-validate what the reader already guarantees.

### `stop_reason_from_u8` is total with explicit unknown-byte rejection

The inverse of `recording::stop_reason_u8` rejects unknown bytes as a log fault rather than
defaulting, and the forward map is cross-pinned against proto in dh-worker's tests. The byte set
(1/2/4/5/6, no 3) matches the forward map exactly.
